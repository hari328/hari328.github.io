AWS — The Infrastructure That Actually Runs Your App

March 24, 202614 min read

You've written the Terraform. You've set up GitHub Actions. Now let's talk about what you're actually building in AWS — and more importantly, why each piece exists.

This isn't a "what is AWS" article. You already know AWS. This is about understanding the architecture decisions behind a production-grade setup, so you're not just copying config — you understand what you're doing and why.

The Big Picture

When your app runs in production, here's what happens at a high level:

Internet
  → Route53 (DNS: api.yourdomain.com → ALB)
    → ALB (HTTPS listener, terminates SSL)
      → Listener rule matches hostname
        → Target group → ECS task (private subnet, port 3000)

Every component in that chain has a reason for existing. Let's walk through them.

VPC — Your Private Network

The first thing Terraform creates is a VPC (Virtual Private Cloud). It's your isolated network inside AWS — nothing gets in or out unless you explicitly allow it.

You pick a CIDR block like 10.0.0.0/16. That gives you 65,536 IP addresses to distribute across everything you'll run.

Why does this matter? Without a VPC, your EC2 instances and databases would be hanging out on the public internet. The VPC is the hard boundary that keeps your infrastructure private.

Subnets — Splitting the Network

A VPC is one big IP range. Subnets split it into smaller pieces for different purposes. The key split is public vs private:

| Subnet           | AZ          | CIDR           | What lives here        |
|------------------|-------------|----------------|------------------------|
| Public Subnet A  | us-east-1a  | 10.0.1.0/24    | ALB, NAT Gateway       |
| Public Subnet B  | us-east-1b  | 10.0.2.0/24    | ALB (redundancy)       |
| Private Subnet A | us-east-1a  | 10.0.10.0/24   | ECS tasks, RDS         |
| Private Subnet B | us-east-1b  | 10.0.20.0/24   | ECS tasks, RDS         |

Two things to notice: your app containers run in private subnets — not directly reachable from the internet. And you span two AZs — if one AWS data center goes down, you're still running in the other.

Internet Gateway (IGW)

Attaches to your VPC and gives public subnets internet access — both inbound and outbound. Without this, your VPC is completely isolated. Nothing works.

NAT Gateway

Here's the problem: your ECS tasks are in private subnets. They can't be reached from the internet (good), but they also can't reach the internet — which means they can't pull Docker images from ECR, call external APIs, or send logs to CloudWatch.

The NAT Gateway solves this. It sits in a public subnet and acts as a translator:

ECS Task (private subnet, IP: 10.0.10.5)
  → NAT Gateway (public subnet)
    → Internet Gateway
      → External service

When your container makes an outbound request, NAT replaces its private IP with a public one, forwards the request, and maps the response back. The internet sees the NAT's IP, not your container's.

Why not just put containers in public subnets? You could — but then your containers are directly reachable from the internet. A misconfigured security group and you've accidentally exposed something you shouldn't. Private subnets are a defense-in-depth choice.

The cost: ~$32/month per NAT Gateway. This is the one unavoidable cost in a proper network setup.

Route Tables

Route tables tell traffic where to go. Every subnet has one.

Public subnet: traffic within 10.0.0.0/16 stays in the VPC; everything else goes to the Internet Gateway.

Private subnet: traffic within 10.0.0.0/16 stays in the VPC; everything else goes to the NAT Gateway.

What Actually Leaves the VPC?

Understanding this matters for both cost and security:

| Traffic                          | Leaves VPC?   | Why                                    |
|----------------------------------|---------------|----------------------------------------|
| ECS → RDS                        | No            | Both inside the VPC                    |
| ECS → another ECS via ALB        | No            | ALB is inside the VPC                  |
| ECS → SQS                        | Yes (via NAT) | SQS is an AWS managed service          |
| ECS → ECR (pull image)           | Yes (via NAT) | ECR is outside your VPC                |
| ECS → CloudWatch (logs)          | Yes (via NAT) | CloudWatch is outside your VPC         |
| ECS → third-party API            | Yes (via NAT) | No alternative                         |

The pattern: resources you deployed inside the VPC (RDS, ElastiCache) stay private. AWS managed services (SQS, ECR, CloudWatch) live outside your VPC and cost NAT data transfer to reach. If those charges add up, VPC PrivateLink lets you route that traffic privately — but that's a later optimization.

ECS — Running Your Containers

ECS (Elastic Container Service) is AWS's container orchestration platform. It answers: given this Docker image, run it somewhere and keep it running.

ECS Cluster

Just a logical namespace. No compute, no cost. You give it a name and ECS knows which group of services belongs together.

resource "aws_ecs_cluster" "main" {
  name = "my-cluster"
}

EC2 vs Fargate

ECS runs containers on either EC2 instances (you manage the machines) or Fargate (AWS manages the machines, you pay per task). This setup uses EC2 — here's why:

  • Cost: On a shared EC2 instance, you pay for capacity whether it's used or not — but that capacity can serve multiple containers. Fargate charges per container. For a monitoring stack + app on one cluster, EC2 is significantly cheaper.
  • Control: EC2 lets you tune instance types, placement, and capacity sharing.

The trade-off: you have to think about instance capacity. Fargate is simpler but more expensive at this scale.

Auto Scaling Group (ASG)

This is the actual fleet of EC2 machines your containers run on. The Launch Template defines what each machine looks like:

  • AMI: amazon-linux-2-ecs-optimized — Amazon's image with the ECS agent pre-installed
  • Instance type: t3.medium (2 vCPU, 4GB RAM)
  • User data — the critical bit:
#!/bin/bash
echo "ECS_CLUSTER=my-cluster" >> /etc/ecs/ecs.config

This one line is how an EC2 instance knows which ECS cluster to join. When the instance boots, the ECS agent reads this file and registers itself with the right cluster.

The ASG manages the fleet: min/max/desired counts, spreads instances across both private subnets (multi-AZ), and scales when ECS needs more capacity.

Capacity Provider

Links the ECS cluster to your ASG. This enables managed scaling — if ECS needs to run a task but no instance has available resources, the capacity provider tells the ASG to launch a new instance. When load drops, it scales back in. Without a capacity provider, you'd manage instance count manually.

ECR — Your Private Docker Registry

ECR (Elastic Container Registry) is where your Docker images live. Your GitHub Actions workflow builds the image and pushes it to ECR. When ECS deploys, it pulls from there.

Why not Docker Hub? ECR is private by default, it's inside AWS (faster pulls, no egress if you use PrivateLink), and IAM controls access — the same role system you use for everything else. Each service gets its own ECR repository, tagged with the Git commit SHA so you can always trace exactly which code is running.

ALB — The Entry Point for All Traffic

The Application Load Balancer sits in your public subnets and is the single entry point for all HTTP/HTTPS traffic.

Why One ALB for Everything?

You could give every service its own ALB, but that's $16/month each. With one ALB, you route to multiple services using listener rules — rules that look at the hostname and forward to the right service:

api.yourdomain.com     → backend-patterns-ts target group
grafana.yourdomain.com → Grafana target group

Same ALB, same IP, different services. The ALB figures out where to send each request.

Listeners

The ALB has two listeners:

  • Port 80 (HTTP): Redirects to 443. Always. You don't want unencrypted traffic.
  • Port 443 (HTTPS): Terminates SSL and forwards to target groups.

Target Groups

A target group is a set of destinations — in this case, ECS tasks. Each service has its own target group with a health check path. ECS tasks that fail health checks get pulled from rotation automatically.

SSL Termination

The ALB holds your SSL certificate and decrypts HTTPS traffic. Your containers never see HTTPS — they receive plain HTTP on port 3000.

User (HTTPS) → ALB (decrypts here) → ECS Task (plain HTTP, port 3000)

Your app code doesn't handle SSL, you don't install certs on containers, and the ALB is already managing the connection — might as well do encryption there.

Security Groups

This is where the "private subnet" story becomes concrete:

ALB security group: inbound on 80 and 443 from 0.0.0.0/0 (the internet can reach the ALB), outbound to everything within the VPC.

EC2 instance security group: inbound from the ALB security group only — nothing else. Outbound to everything.

Your EC2 instances are completely unreachable from the internet. The only way to send traffic to them is through the ALB. If someone finds your instance's IP and tries to connect directly — the security group drops it.

IAM — Who Can Do What

IAM is the permission system. It answers: is this thing allowed to do that? In this setup there are two important roles.

EC2 Instance Profile

The EC2 machines need permissions to: register with ECS, pull images from ECR, write logs to CloudWatch, and read SSM parameters. This is attached via an IAM instance profile — the machines get a role with exactly those permissions, nothing more.

ECS Task Role

Each ECS service also gets its own IAM role, separate from the instance role. Your app might need to send messages to SQS, read from S3, or access Secrets Manager. The task role carries those permissions. When your code uses the AWS SDK, it automatically picks up the task role credentials — no access keys, no secrets in environment variables.

Why separate task role from instance role? Least privilege. Your app shouldn't have permission to register ECS instances or pull images — that's the machine's job. If your app is compromised, a scoped task role limits what an attacker can reach.

Route53 + ACM — DNS and SSL

Route53

Route53 is AWS's DNS service. It translates api.yourdomain.com to your ALB's IP. You create a hosted zone for your domain, then ALIAS records for each subdomain pointing to the ALB. All subdomains hit the same ALB — listener rules sort out where each goes.

You can buy the domain anywhere (Namecheap, Google Domains). You just update the domain's nameservers to point to Route53.

ACM — Free SSL Certificates

ACM (AWS Certificate Manager) issues and auto-renews SSL certificates for free. You request a wildcard certificate for *.yourdomain.com — one cert covers all your subdomains.

AWS validates ownership via DNS: you create a record in Route53 (Terraform does this automatically), ACM sees it and issues the cert. That record stays permanently and ACM uses it to auto-renew every year. Zero maintenance.

Putting It All Together

Here's the full request lifecycle:

1. User hits api.yourdomain.com
2. Route53 resolves to ALB's IP
3. Request hits ALB on port 443
4. ALB decrypts HTTPS using ACM wildcard cert
5. Listener rule matches hostname → routes to backend target group
6. Target group picks a healthy ECS task
7. Request reaches container on port 3000 (plain HTTP)
8. Container processes request
9. If it needs SQS → NAT Gateway → Internet → SQS
10. If it needs to log → NAT Gateway → CloudWatch

Every hop is intentional. Every component is doing exactly one job.

Cost Summary

| Component                          | Monthly Cost |
|------------------------------------|--------------|
| VPC, subnets, IGW, route tables    | Free         |
| NAT Gateway                        | ~$32         |
| ECS Cluster                        | Free         |
| t3.medium EC2 (1 instance)         | ~$30         |
| ALB                                | ~$16         |
| Route53 hosted zone                | $0.50        |
| ACM certificate                    | Free         |
| ECR                                | ~$1          |
| Total                              | ~$80/month   |

For a production-grade platform running multiple services with HTTPS, multi-AZ, and auto-scaling — $80/month is reasonable.

What You Actually Own

After all this Terraform runs, you own:

  • A private network that's properly segmented
  • Containers that can't be reached directly from the internet
  • A single entry point (ALB) that enforces HTTPS and routes by hostname
  • An auto-scaling compute layer that responds to load
  • DNS and SSL that auto-renew and require zero maintenance
  • IAM roles scoped to exactly what each component needs
