Terraform + Terragrunt

March 23, 20268 min read

What is IaC?

Infrastructure as Code (IaC) is a way to provision and manage infrastructure using code instead of manual processes. It lets you define your infrastructure in a declarative way, making it easier to version, test, and deploy changes.

IaC is one of the leading ways to deploy infrastructure for any SaaS product. There are other tools for it, but Terraform is the most popular — it supports multiple cloud providers, is open source, has a large community, and is simple to learn.

Terraform's core idea is declarative code: you define what you want, and Terraform figures out how to get there. It uses a domain-specific language called HCL (HashiCorp Configuration Language).

The Problem with Vanilla Terraform

Terraform stores the state of your infrastructure in a state file. By default, that file lives locally — which breaks down immediately when multiple developers are working on the same infrastructure.

You can move to remote state (S3 + DynamoDB for AWS), but now you've added setup overhead, and you still haven't solved the bigger problem: how do you manage multiple environments (dev, stage, prod) without repeating yourself?

That's where Terragrunt comes in.

Terragrunt

Terragrunt is a thin wrapper around Terraform. It solves three things that vanilla Terraform handles poorly:

  1. Remote state management — automatically creates and configures S3 + DynamoDB state backends per module, per environment
  2. DRY configuration — a root config file is inherited by all child modules; no repeated provider or backend boilerplate
  3. Environment isolation — stage and prod are separate folder trees sharing the same module code

I learned Terraform and Terragrunt hands-on from Terraform: Up and Running. I'd recommend coding along with the book — having hands-on confidence with Terraform is non-negotiable for any developer working in the cloud today.

Repo Structure

The infra-backend-patterns-ts repo shows how this works in practice:

terraform/
├── terragrunt.hcl          ← root config, inherited by all modules
├── modules/                ← reusable terraform modules
├── stage/
│   ├── env.yaml            ← environment: stage, region: us-east-1
│   └── us-east-1/
│       └── base-infra/
│           ├── networking/terragrunt.hcl
│           ├── dns-ssl/terragrunt.hcl
│           ├── alb/terragrunt.hcl
│           ├── ecs-cluster/terragrunt.hcl
│           └── github-actions-app-deploy-role/terragrunt.hcl
└── prod/
    ├── env.yaml            ← environment: prod, region: us-east-1
    └── us-east-1/
        └── base-infra/
            ├── networking/terragrunt.hcl
            ├── dns-ssl/terragrunt.hcl
            ├── alb/terragrunt.hcl
            ├── ecs-cluster/terragrunt.hcl
            └── github-actions-app-deploy-role/terragrunt.hcl

Same modules, different env.yaml — prod gets its own state bucket and lock table automatically via the root config.

4 Key Patterns

1. DRY via root inheritance

The root terragrunt.hcl defines the provider and S3 backend once. Every child config inherits it with a single line:

include "root" {
  path = find_in_parent_folders()
}

No repeated boilerplate across 10 modules across 2 environments.

2. Environment isolation

Each environment (stage, prod) is its own folder tree with its own env.yaml. Switching environments means switching folders — the module code is identical.

3. Explicit dependency wiring

Modules declare dependencies using dependency blocks, which enforce apply order and pass outputs directly as inputs — no manual copy-pasting of resource IDs between modules.

dependency "networking" {
  config_path = "../networking"
}

inputs = {
  vpc_id     = dependency.networking.outputs.vpc_id
  subnet_ids = dependency.networking.outputs.private_subnet_ids
}

4. Isolated state per module — how Terragrunt stores state in S3

Each module gets its own .tfstate file in S3. A change to alb doesn't touch networking state — safe, granular applies with no blast radius.

Each environment folder has an env.yaml that declares which environment and region it belongs to:

# terraform/stage/env.yaml
aws_region:  us-east-1
environment: stage
project:     hari328

The root terragrunt.hcl reads that file and wires up the S3 backend for every module automatically:

locals {
  env_vars    = yamldecode(file("${find_in_parent_folders("env.yaml")}"))
  aws_region  = local.env_vars["aws_region"]
  environment = local.env_vars["environment"]
  project     = local.env_vars["project"]
}

remote_state {
  backend = "s3"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite_terragrunt"
  }
  config = {
    bucket         = "hari328-infra-${local.environment}-tfstate"
    key            = "${path_relative_to_include()}/terraform.tfstate"
    region         = local.aws_region
    encrypt        = true
    dynamodb_table = "hari328-infra-${local.environment}-tflock"
  }
}

The critical piece is path_relative_to_include(). Terragrunt replaces that with the module's folder path relative to the root config — so the S3 key is derived automatically from where the module lives in the repo. This is what the actual S3 buckets look like:

hari328-infra-stage-tfstate/          ← one bucket per environment
└── stage/
    └── us-east-1/
        └── base-infra/
            ├── networking/
            │   └── terraform.tfstate
            ├── dns-ssl/
            │   └── terraform.tfstate
            ├── alb/
            │   └── terraform.tfstate
            ├── ecs-cluster/
            │   └── terraform.tfstate
            └── github-actions-app-deploy-role/
                └── terraform.tfstate

hari328-infra-prod-tfstate/           ← completely separate bucket
└── prod/
    └── us-east-1/
        └── base-infra/
            ├── networking/
            │   └── terraform.tfstate
            ├── ...
            └── ecs-cluster/
                └── terraform.tfstate

You never write any of this manually. The folder structure in the repo is the S3 key path — Terragrunt derives it automatically via path_relative_to_include(). Add a new module folder, and its state file appears in the right place on the first apply.

The DynamoDB table (hari328-infra-stage-tflock) provides state locking — if one engineer is running apply on networking, a second engineer's apply on the same module is blocked until the first one finishes. Each module has its own lock entry, so an apply on alb never blocks an apply on ecs-cluster.

Takeaway

Terragrunt is what makes Terraform production-ready. It solves the three real-world problems vanilla Terraform doesn't handle well: shared remote state, DRY config across environments, and dependency ordering between modules. If you're deploying anything beyond a single environment, reach for Terragrunt.
